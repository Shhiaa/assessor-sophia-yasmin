diagnóstico

O regex do MongoDB é frágil para IA

O $regex do MongoDB faz correspondência textual exata — no máximo case-insensitive. Se o resumo diz "viagem para Salvador" e o agente busca "viajar", "destino" ou "férias", o regex retorna zero resultados. A IA gera sinônimos naturalmente — o mecanismo de busca precisa acompanhar.

BuscaResultadoPor quê
viagem✓ 1 resultadosubstring exata encontrada no resumo
Salvador✓ 1 resultadosubstring exata encontrada
viajar✕ 0 resultados"viajar" ≠ "viagem" — radicais diferentes
destino✕ 0 resultadossinônimo, mas o regex não sabe disso
férias✕ 0 resultadosconceito relacionado, texto diferente
moveis✕ 0 resultados"moveis" ≠ "móveis" — sem acento não casa
O agente está certo — a busca está errada

O agente está certo ao dizer "não encontrei nada" — o problema não é ele, é a busca. A arquitetura está correta; a recuperação é que é frágil.

diagnóstico

O FAISS recria o índice a cada pergunta

Olhando o tools/faq.py atual, cada chamada da tool faz: carregar PDF → split → gerar embeddings de todos os chunks → criar índice FAISS → buscar. Isso é desnecessário e caro.

app/tools/faq.py — código atual (antes da migração)
o problemaClique para ver
@tool def faq_retriever(question: str) -> str: """Busca no FAQ oficial os trechos mais relevantes.""" splitter = RecursiveCharacterTextSplitter(chunk_size=700, chunk_overlap=150) chunks = splitter.split_documents(docs) # ← recria os chunks TODA VEZ embeddings = GoogleGenerativeAIEmbeddings( model="gemini-embedding-2-preview", google_api_key=GEMINI_API_KEY, ) db = FAISS.from_documents(chunks, embeddings) # ← reconstrói o índice TODA VEZ results = db.similarity_search(question, k=6) return "\n\n".join([t.page_content for t in results])
O custo escondido

O PDF tem ~15 chunks. A cada pergunta de FAQ, o sistema gera 15 embeddings (chamadas de API ao Gemini), reconstrói o índice em memória, e depois faz a busca. Se o PDF tivesse 500 páginas, seriam centenas de embeddings por pergunta. O FAISS é bom para prototipar — em produção, precisamos de indexação separada da consulta.

solução

Qdrant: um banco vetorial para tudo

O Qdrant é um banco de dados vetorial que armazena embeddings e permite busca por similaridade semântica. Diferente do regex (texto exato), ele compara o significado. Uma única infraestrutura resolve os dois problemas: memória e FAQ.

Antes

  • $regex no MongoDB para memória — perde sinônimos
  • FAISS reconstruído a cada chamada para FAQ — lento e caro
  • Busca textual: "viajar" nunca encontra "viagem"

Depois

  • Qdrant para memória e FAQ — uma só infraestrutura
  • Indexação uma vez, consulta sempre — rápido e barato
  • "viajar" encontra "viagem para Salvador" — semântica

Duas collections, dois propósitos

teoria

Por dentro do Qdrant: Point, Vector e Payload

Antes de configurar, vale entender o que o Qdrant armazena. A unidade básica é o Point — o equivalente a um "documento" no MongoDB, mas pensado para busca por significado.

Um Point tem três partes

🆔 id

Identificador único do ponto. Pode ser UUID ou inteiro. No nosso caso, usamos o mesmo doc_id do MongoDB — assim podemos ir do Qdrant ao Mongo para buscar detalhes.

📐 vector

Uma lista de números (768 floats no nosso caso) gerada pelo modelo de embedding. Representa o significado do texto. Textos com sentidos parecidos têm vetores parecidos.

📦 payload

JSON livre com metadados — como um documento no MongoDB. Você coloca o que quiser: resumo, user_id, page_content. O Qdrant guarda e devolve, mas não busca por ele — ele busca pelo vetor.

MongoDB doc vs Qdrant point

ConceitoMongoDBQdrant
Unidade de dadosDocument (JSON)Point (id + vector + payload)
Identificador_idid
Metadados livresCampos do documentopayload (JSON livre, igual)
DiferencialNão tem vetorO vector — 768 números que codificam o significado
Busca principalPor campo: {"nome": "João"}Por similaridade do vetor (semântica)
AgrupamentoCollectionCollection (mesmo nome, mesmo conceito)
Payload ≠ vetor na busca

O payload é devolvido junto com o resultado, mas a busca em si é feita pelo vetor. É como se o vetor fosse o "índice de busca" e o payload fosse o "conteúdo que volta". Você pode até filtrar pelo payload (ex: user_id == "marcelo"), mas a ordenação dos resultados é por similaridade vetorial, não textual.

teoria

As duas operações: upsert e query_points

No nosso código, só usamos duas operações do Qdrant. Entendê-las é entender todo o fluxo.

⬆️ upsert — gravar um ponto

Quando: ao encerrar uma sessão (encerrar_sessao) e ao indexar os chunks do PDF (ingest_faq).

O que faz: insere um ponto novo ou atualiza se o id já existir (update + insert = upsert).

Você envia: id + vector (embedding do texto) + payload (metadados JSON).

🔍 query_points — buscar por significado

Quando: ao buscar na memória (recuperar_historico) e ao responder FAQ (faq_retriever).

O que faz: recebe o vetor da pergunta, compara com todos os vetores da collection por similaridade de cosseno, e retorna os mais parecidos.

Você envia: query (vetor da pergunta) + limit + query_filter (opcional).

Similaridade de cosseno — como o match funciona

Quando você faz uma busca, o Qdrant não compara palavras — compara vetores. Cada texto virou uma lista de 768 números. A similaridade de cosseno mede o ângulo entre dois vetores:

≈ 1.0

Significados quase idênticos

"viagem" ↔ "viajar"

≈ 0.5

Alguma relação

"viagem" ↔ "mala"

≈ 0.0

Sem relação

"viagem" ↔ "imposto"

O Qdrant calcula o cosseno entre o vetor da pergunta e cada ponto da collection, ordena do mais similar ao menos, e devolve os limit primeiros — junto com o payload completo.

E o query_filter?

O filtro age antes da busca vetorial — como um WHERE no SQL. No nosso caso, usamos para restringir a busca ao user_id do usuário atual:

Exemplo simplificado de query_points
conceitoClique para ver
qdrant.query_points( collection_name="memoria_resumos", query=vetor_da_pergunta, # [0.12, -0.34, 0.56, ... 768 floats] query_filter=models.Filter( # WHERE user_id = "usuario_teste" must=[ models.FieldCondition( key="user_id", match=models.MatchValue(value="usuario_teste"), ) ] ), limit=3, # top 3 mais similares )
Fluxo completo em uma frase

O Qdrant filtra os pontos pelo payload (user_id), calcula a similaridade de cosseno entre o vetor da pergunta e o vetor de cada ponto que passou no filtro, ordena do mais similar ao menos, e devolve os top N — cada um com id, score e payload completo.

Por que 768 e não 3072?

O Gemini Embedding 2 gera até 3072 dimensões, mas o Google recomenda 768 para produção — qualidade quase idêntica com 1/4 do armazenamento. Basta passar output_dimensionality=768 ao gerar embeddings.

O problema da identidade entre sessões O session_id muda — e leva a memória junto.

O session_id que o frontend envia muda a cada sessão (é um UUID novo). Quando encerramos uma sessão, salvamos o resumo no Qdrant com esse session_id. Mas na sessão seguinte, o session_id é outro — e o filtro de multitenancy no Qdrant procura só pelo id atual, que nunca vai encontrar resumos de sessões anteriores.

Front gera UUID novo
→
session_id da sessão 2 ≠ sessão 1
→
Filtro no Qdrant não encontra nada
→
Memória de longo prazo quebrada

A solução: introduzir um user_id estável — que não muda entre sessões. O session_id continua existindo para o checkpointer (contexto da conversa atual), mas a memória de longo prazo filtra pelo user_id.

IdentificadorMuda a cada sessão?Para quê serve
session_idSimCheckpointer (contexto da conversa atual)
user_idNãoMemória de longo prazo (busca entre sessões)

Vamos adicionar user_id como campo opcional no ChatRequest, com valor padrão 'usuario_teste'. Assim não quebra nada no frontend existente.

""" ================= Modelagem --------- Um documento por acesso (sessão = uma conversa completa). O _id é um UUID gerado internamente. O session_id identifica a CONVERSA (UUID do front, muda a cada sessão). O user_id identifica o USUÁRIO (estável entre sessões — necessário para memória). Documento --------- { "_id": "uuid-gerado-internamente", "session_id": "uuid-da-conversa", "user_id": "usuario_teste", "iniciada_em": datetime, "atualizada_em": datetime, "resumo": "Usuário registrou Pix de R$50...", "mensagens": [ {"role": "usuario", "content": "oi"}, {"role": "assistente", "content": "Olá!"} ] } Funções ---------------- iniciar_sessao(session_id, user_id) → cria documento no MongoDB salvar_mensagem(session_id, role, content) → adiciona mensagem na sessão ativa encerrar_sessao(session_id) → gera resumo e salva no documento + Qdrant """ import uuid from datetime import datetime, timezone from app.llms import llm_rapido from pymongo import MongoClient from qdrant_client import models from app.config import MONGODB_URI from app.vectorstore import qdrant, gerar_embedding, COLLECTION_MEMORIA _mongo = MongoClient(MONGODB_URI) db = _mongo["assessor"] col_sessoes = db["sessoes"] col_sessoes.create_index("session_id") col_sessoes.create_index("user_id") col_sessoes.create_index("iniciada_em") _PROMPT_RESUMO = """\ Você é um assistente que resume conversas de assessoria financeira e agenda. Gere um resumo conciso em 2-4 frases capturando: - O que o usuário fez (transações registradas, eventos agendados) - O que o usuário perguntou - Informações relevantes mencionadas (valores, datas, categorias) Responda APENAS com o resumo, sem introdução ou explicação. Conversa: {conversa} """ _sessoes_ativas: dict = {} def _agora() -> datetime: return datetime.now(timezone.utc) def _formatar_conversa(mensagens: list[dict]) -> str: """Formata o array de mensagens em texto para o prompt de resumo.""" linhas = [] for msg in mensagens: linhas.append(f"{msg['role']}: {msg['content']}") return "\n".join(linhas) def _gerar_resumo(mensagens: list[dict]) -> str: """Chama o LLM para gerar o resumo da sessão.""" conversa = _formatar_conversa(mensagens) return llm_rapido.invoke( _PROMPT_RESUMO.format(conversa=conversa) ).content.strip() def _doc_id_da_sessao(session_id: str) -> str | None: doc_id = _sessoes_ativas.get(session_id) if doc_id: return doc_id doc = col_sessoes.find_one( {"session_id": session_id, "resumo": {"$in": ["", None]}}, {"_id": 1}, sort=[("iniciada_em", -1)], ) if not doc: return None _sessoes_ativas[session_id] = doc["_id"] return doc["_id"] def iniciar_sessao(session_id: str, user_id: str = "usuario_teste") -> None: if _doc_id_da_sessao(session_id): return doc_id = str(uuid.uuid4()) agora = _agora() col_sessoes.insert_one({ "_id": doc_id, "session_id": session_id, "user_id": user_id, "iniciada_em": agora, "atualizada_em": agora, "resumo": "", "mensagens": [], }) _sessoes_ativas[session_id] = doc_id def salvar_mensagem( session_id: str, role: str, content: str, user_id: str = "usuario_teste" ) -> None: iniciar_sessao(session_id, user_id=user_id) doc_id = _doc_id_da_sessao(session_id) col_sessoes.update_one( {"_id": doc_id}, { "$push": {"mensagens": {"role": role, "content": content}}, "$set": {"atualizada_em": _agora()}, }, ) def encerrar_sessao(session_id: str) -> str: doc_id = _doc_id_da_sessao(session_id) if not doc_id: return "" doc = col_sessoes.find_one({"_id": doc_id}) if not doc or not doc.get("mensagens"): _sessoes_ativas.pop(session_id, None) return "" resumo = _gerar_resumo(doc["mensagens"]) col_sessoes.update_one( {"_id": doc_id}, {"$set": {"resumo": resumo, "atualizada_em": _agora()}}, ) # Salva o embedding do resumo no Qdrant para busca semântica futura. # O filtro de multitenancy usa user_id (estável entre sessões), não session_id. user_id = doc.get("user_id", "usuario_teste") vetor = gerar_embedding(resumo) qdrant.upsert( collection_name=COLLECTION_MEMORIA, points=[ models.PointStruct( id=doc_id, vector=vetor, payload={ "user_id": user_id, "session_id": session_id, "resumo": resumo, "iniciada_em": doc["iniciada_em"].isoformat(), }, ) ], ) _sessoes_ativas.pop(session_id) return resumo def recuperar_historico(user_id: str, busca: str = "", limite: int = 3) -> list[dict]: if busca: vetor = gerar_embedding(busca) resultados = qdrant.query_points( collection_name=COLLECTION_MEMORIA, query=vetor, query_filter=models.Filter( must=[ models.FieldCondition( key="user_id", match=models.MatchValue(value=user_id), ) ] ), limit=limite, ) if resultados.points: return [ { "doc_id": ponto.id, "iniciada_em": ponto.payload.get("iniciada_em", ""), "resumo": ponto.payload["resumo"], } for ponto in resultados.points ] filtro = {"user_id": user_id, "resumo": {"$nin": ["", None]}} docs = ( col_sessoes .find(filtro, {"resumo": 1, "iniciada_em": 1}) .sort("iniciada_em", -1) .limit(limite) ) return [ {"doc_id": d["_id"], "iniciada_em": d["iniciada_em"], "resumo": d["resumo"]} for d in docs ] def recuperar_mensagens(doc_id: str) -> list[dict]: doc = col_sessoes.find_one({"_id": doc_id}, {"mensagens": 1}) return doc["mensagens"] if doc else []
MongoDB continua sendo o armazém

O MongoDB continua sendo o armazém das mensagens e metadados. O Qdrant é apenas o índice de busca semântica — ele guarda o vetor e o payload mínimo (resumo, user_id, data), e retorna o doc_id que aponta para o documento completo no MongoDB.

""" Script de ingestão do FAQ no Qdrant. Lê o PDF, faz split em chunks, gera embeddings e insere na collection "faq_chunks" do Qdrant. Deve ser executado UMA VEZ (ou sempre que o PDF mudar): python -m app.ingest_faq Ele limpa a collection antes de reinserir, então é seguro rodar várias vezes. """ import uuid from langchain_community.document_loaders import PyPDFLoader from langchain_text_splitters import RecursiveCharacterTextSplitter from qdrant_client import models from app.config import FAQ_PDF_PATH from app.vectorstore import qdrant, gerar_embeddings_batch, COLLECTION_FAQ CHUNK_SIZE = 700 CHUNK_OVERLAP = 150 BATCH_SIZE = 50 def ingerir_faq() -> int: """Indexa o PDF do FAQ no Qdrant. Retorna o número de chunks inseridos.""" print(f"[ingest] Carregando PDF: {FAQ_PDF_PATH}") loader = PyPDFLoader(str(FAQ_PDF_PATH)) docs = loader.load() print(f"[ingest] {len(docs)} página(s) carregada(s)") splitter = RecursiveCharacterTextSplitter( chunk_size=CHUNK_SIZE, chunk_overlap=CHUNK_OVERLAP, ) chunks = splitter.split_documents(docs) print(f"[ingest] {len(chunks)} chunk(s) gerado(s)") info = qdrant.get_collection(COLLECTION_FAQ) if info.points_count > 0: print(f"[ingest] Limpando {info.points_count} ponto(s) existente(s)...") qdrant.delete( collection_name=COLLECTION_FAQ, points_selector=models.FilterSelector( filter=models.Filter(must=[]) ), ) textos = [chunk.page_content for chunk in chunks] for i in range(0, len(textos), BATCH_SIZE): lote_textos = textos[i : i + BATCH_SIZE] lote_chunks = chunks[i : i + BATCH_SIZE] print(f"[ingest] Gerando embeddings para chunk {i+1}–{i+len(lote_textos)}...") vetores = gerar_embeddings_batch(lote_textos) pontos = [ models.PointStruct( id=str(uuid.uuid4()), vector=vetor, payload={ "page_content": chunk.page_content, "page_number": chunk.metadata.get("page", 0), "source": str(chunk.metadata.get("source", "")), }, ) for vetor, chunk in zip(vetores, lote_chunks) ] qdrant.upsert(collection_name=COLLECTION_FAQ, points=pontos) print(f"[ingest] Concluído! {len(chunks)} chunk(s) indexado(s) no Qdrant.") return len(chunks) if __name__ == "__main__": ingerir_faq()

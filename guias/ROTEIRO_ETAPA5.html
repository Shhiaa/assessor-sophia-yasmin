Pré-requisitos

A Etapa 2 precisa estar no ar: Postgres com a tabela transactions, tools em app/tools/financeiro.py e o chat do Assessor respondendo sobre saldo e gastos. O container pg (ou o Postgres local) tem que estar ligado — o servidor MCP usa a mesma DATABASE_URL.

diagnóstico

As tools só servem este grafo

Hoje o agente financeiro chama add_transaction porque o graph.py importou a lista TOOLS. Isso é function calling dentro do mesmo processo. O Cursor não importa Python. O Cline não conhece LangChain. Um colega em Node não consegue usar o saldo de vocês.

O que temos hoje

  • @tool LangChain, acoplada ao grafo
  • Só quem importa financeiro.py usa a tool
  • Trocar o framework = reescrever a integração
  • O chat do Assessor é o único cliente

O que MCP entrega

  • Contrato padrão, independente de linguagem
  • O SQL continua num lugar só
  • Cursor, Cline e o Assessor falam o mesmo protocolo
  • Descoberta em runtime: list_tools → call_tool
Não é “mais uma tool”

Se o objetivo fosse só consultar saldo, a @tool já faz isso. MCP só vale quando quem tem a capacidade e quem usa a capacidade não são o mesmo programa. Esta etapa prova isso: o Cursor consulta o banco de vocês sem abrir o FastAPI.

teoria

MCP é um protocolo, não uma biblioteca

Model Context Protocol — Protocolo de Contexto do Modelo. É um padrão aberto que descreve como um aplicativo de IA conversa com ferramentas e dados externos. A analogia certa não é “pacote Python”. É HTTP: um acordo de mensagens que qualquer um pode implementar.

📜 Especificação

O contrato: quais mensagens existem, o formato JSON-RPC, o handshake, as primitivas. Publicada em modelcontextprotocol.io.

🧰 SDKs

Implementações em Python, TypeScript, Java, Kotlin, C#, Go, Rust… Nós usamos o SDK Python. O Cursor usa o de TypeScript. O protocolo é o mesmo.

🔌 Servidores e clientes

Quem expõe capacidade é servidor. Quem consome é cliente. Nesta etapa o Assessor é servidor; o Cursor é cliente.

HTTP é o contrato entre o navegador e o FastAPI. MCP é o contrato entre um modelo e uma ferramenta. Os dois resolvem o mesmo tipo de problema: dois programas diferentes precisam conversar sem importar o código um do outro.
teoria

MCP não é “da Google” nem “da OpenAI”. Começou dentro da Anthropic, foi aberto ao mundo e hoje é governado fora de uma empresa só — o mesmo caminho que Linux e Kubernetes fizeram.

Por que isso importa na disciplina

Vocês estão aprendendo um padrão da indústria, não um recurso de um fornecedor. Cursor, Claude, VS Code, Gemini CLI e o Google Calendar MCP falam o mesmo idioma. Daqui a dois anos o cliente pode mudar; o contrato permanece.

teoria

A inspiração: LSP e o problema M × N

O Language Server Protocol (Microsoft, 2016) resolveu um problema idêntico para editores: sem padrão, cada editor precisava de um plugin para cada linguagem — VS Code × Python, Vim × Python, VS Code × Rust… Isso é M editores × N linguagens integrações. Com LSP, cada editor implementa o cliente uma vez e cada linguagem implementa o servidor uma vez: M + N.

Antes — M × N

5 agentes × 8 sistemas = 40 conectores artesanais. Cada um com auth, schema e bugs próprios. Trocar o modelo = reescrever tudo.

Depois — M + N

5 clientes MCP + 8 servidores MCP = 13 implementações. O Assessor publica um servidor; Cursor, Cline e o colega conectam sem pedir o código.

A frase para lembrar

LSP padronizou “como o editor fala com a linguagem”. MCP padroniza “como o modelo fala com a ferramenta”. Vocês já viram o equivalente HTTP na migração para FastAPI. É o mesmo raciocínio, terceira vez: contrato entre processos.

teoria

Quem é o cliente e quem é o servidor

Os nomes confundem porque “servidor” parece o FastAPI. Em MCP, servidor é quem oferece ferramentas. Pode ser um script Python na sua máquina, falando pela entrada e saída padrão. Não precisa de porta 8000.

Host O aplicativo com o modelo: Cursor, Cline, Claude Desktop, o Assessor. Ele orquestra a conversa.
Cliente MCP O pedaço do host que fala o protocolo. Lista tools, chama tools, mostra o resultado para o modelo.
Servidor MCP O processo que tem a capacidade. No nosso caso: app/mcp_server.py + Postgres.

teoria

Três primitivas: tools, resources, prompts

A spec não é só “chamar função”. São três tipos de oferta. Nesta etapa usamos só a primeira — mas vocês precisam conhecer as três para não achar que MCP = tool calling com outro nome.

🛠️ Tools

Quem decide: o modelo.

Funções com schema JSON. Podem ler e escrever. Ex.: total_balance, add_transaction. Métodos: tools/list, tools/call.

📦 Resources

Quem decide: o aplicativo / o usuário.

Dados passivos, em geral só leitura: um arquivo, o schema do banco, um PDF. O modelo não “clica” sozinho. Ex.: o FAQ como recurso, não como tool.

💬 Prompts

Quem decide: o usuário.

Templates prontos (“feche o mês”, “prepare a reunião”). O cliente mostra no menu; a pessoa escolhe. Não é o modelo inventando a chamada.

Por que começamos por tools

É o que vocês já têm no LangChain. A distância conceitual é a menor: a mesma função, outra porta. Resources e prompts entram depois, quando o servidor de agenda e o FAQ ganharem cara de “documento”, não só de “ação”.

teoria

Como as mensagens viajam

A camada de dados é JSON-RPC 2.0 (pedido com id, método, params; resposta com result ou error). Embaixo disso, o transporte — o cano por onde o JSON passa.

stdio — o que usamos hoje

O cliente sobe o servidor como processo filho e conversa pela entrada/saída padrão. Não tem URL, não tem porta, não tem CORS. É o modo do .cursor/mcp.json com command + args.

Streamable HTTP — o próximo

O servidor já está no ar, o cliente aponta para uma URL. É o caso do Google Calendar MCP: https://calendarmcp.googleapis.com/mcp/v1. Entra OAuth. Não é desta aula.

1initializeCliente e servidor combinam versão e capacidades.
2tools/listO servidor devolve o catálogo: nome, descrição, schema de argumentos.
3tools/callO modelo escolhe uma tool; o cliente pede execução; o servidor devolve o resultado.
stdout é o protocolo

Em stdio, print("oi") no servidor quebra a conexão: o cliente espera JSON-RPC e recebe texto solto. Log vai para sys.stderr. Isso aparece de propósito no código desta etapa.

teoria

API e MCP não são a mesma coisa

A pergunta que sempre vem: “por que não exponho um GET /saldo no FastAPI?” Dá. Vocês já fizeram isso com o chat. A diferença não é “um é moderno”. É quem está do outro lado e o que o contrato assume.

FastAPI continua sendo a porta do usuário. @tool continua sendo a porta do grafo. MCP é a porta de outro agente. Não substituímos nada nesta etapa — acrescentamos uma porta.

teoria

O teste de uma frase: mesmo processo?

Antes de criar um MCP, pergunte: essa capacidade já vive no mesmo Python que o agente? Se sim, @tool ganha. MCP é overhead. Se não — outro app, outra equipe, outra linguagem, outro aluno — aí o protocolo paga o custo.

Não use MCP

  • Cotação de dólar com um GET que vocês controlam
  • Feriado da BrasilAPI encapsulado numa tool
  • E-mail com smtplib no mesmo arquivo
  • “Para parecer moderno” em cima de função interna

Use MCP

  • O Cursor precisa do saldo sem importar o projeto
  • O Assessor consome o Calendar da Google
  • A turma B usa as tools da turma A sem copiar SQL
  • Trocar o cérebro (Ollama → outro) sem reescrever as mãos
Pergunta de prova

“Dá para buscar cotação via MCP?” Sim. “Devemos?” Em geral não: o Assessor já é Python e a API é um GET. MCP brilha quando vocês não escrevem o outro lado — ou quando o outro lado não pode importar o vosso código.

teoria

Utilidades que vocês já viram sem saber o nome

O Cursor que vocês usam agora é um host MCP. Quando alguém “liga o GitHub” ou “liga o banco” nas configurações, está apontando um cliente para um servidor. A ideia desta etapa é vocês estarem do outro lado da tomada.

IDE como cliente

Cursor e Cline leem arquivos, git, e agora o Assessor. O modelo ganha mãos no seu ambiente sem cada ferramenta virar plugin específico.

Empresa como servidor

Google Calendar, Gmail, Notion, GitHub publicam MCP oficial. Vocês não reimplementam a API: autenticam e descobrem as tools.

Produto como plataforma

O Assessor deixa de ser só um chat. Vira capacidade. Qualquer agente da escola pode perguntar o saldo, com a permissão certa.

O recorte desta aula

Um servidor, cinco tools que já existiam, dois clientes (Cursor e Cline). Sem OAuth, sem Google, sem o Assessor como cliente. Isso vem nas próximas aulas — e só faz sentido depois que vocês sentirem o protocolo na pele.

estruturaClique para ver
import sys from pathlib import Path from typing import Annotated, Any, Optional BASE_DIR = Path(__file__).resolve().parent.parent if str(BASE_DIR) not in sys.path: sys.path.insert(0, str(BASE_DIR)) from mcp.server.mcpserver import MCPServer from mcp.types import ToolAnnotations from pydantic import Field from app.tools.financeiro import ( add_transaction as _add_transaction, daily_balance as _daily_balance, query_transactions as _query_transactions, total_balance as _total_balance, update_transaction as _update_transaction, ) mcp = MCPServer( name="assessor-financeiro", version="1.0.0", instructions="Ferramentas financeiras do Assessor.AI...", ) LEITURA = ToolAnnotations(readOnlyHint=True) ESCRITA = ToolAnnotations(readOnlyHint=False, destructiveHint=False)
Por que o sys.path

O cliente MCP executa python app/mcp_server.py com cwd qualquer. Sem colocar a raiz do projeto no sys.path, o from app.tools.financeiro import ... quebra. É o mesmo truque de “rodar o módulo como script”.

bloco A · servidor

A tool MCP é uma casca

Não reescrevemos o SQL. A função MCP declara o contrato (tipos + descrições para o modelo) e despacha para a tool que o LangChain já conhece. .invoke({...}) é o jeito oficial de chamar uma @tool como função Python.

app/mcp_server.py — total_balance e add_transaction (recorte)
ideia centralClique para ver
@mcp.tool( name="total_balance", title="Saldo total", description="Saldo de todo o histórico: receitas menos despesas.", annotations=LEITURA, ) def total_balance() -> dict[str, Any]: return _total_balance.invoke({}) @mcp.tool( name="add_transaction", title="Registrar transação", description="Registra uma transação na tabela transactions.", annotations=ESCRITA, ) def add_transaction( amount: Annotated[float, Field(description="Valor (sempre positivo).")], source_text: Annotated[str, Field(description="Texto original.")], type_name: Annotated[Optional[str], Field(description="INCOME | EXPENSES | TRANSFER")] = None, category_name: Annotated[Optional[str], Field(description="Categoria em pt-BR.")] = None, ... ) -> dict[str, Any]: return _add_transaction.invoke({ "amount": amount, "source_text": source_text, "type_name": type_name, "category_name": category_name, ... })
O argumento da aula, em uma linha

MCP não é uma nova implementação. É uma nova porta para a mesma capacidade. Se o INSERT mudar amanhã, vocês mexem em financeiro.py uma vez — o servidor MCP e o grafo herdam juntos.

bloco A · servidor

O contrato MCP não é espelho da tool interna

A tool LangChain aceita type_id e category_id. Um cliente de fora não tem como saber que 1 = INCOME ou qual é o id de “comida”. No servidor MCP publicamos os nomes e deixamos a tool interna resolver os ids. Escolher o que expor é desenhar API — vocês já fizeram isso no FastAPI com Pydantic.

ToolLeitura / escritaPapel
query_transactionsleituraLista com filtros de texto, tipo e data (São Paulo)
total_balanceleituraReceitas − despesas no histórico
daily_balanceleituraSaldo de um dia YYYY-MM-DD
add_transactionescritaINSERT — pede confirmação no Cursor
update_transactionescritaUPDATE por id ou por texto+data
readOnlyHint

As anotações readOnlyHint=True e destructiveHint=False viajam no protocolo. O Cursor usa isso para decidir o que pode rodar sozinho e o que pede o seu “Allow”. Não é segurança de verdade (o cliente pode ignorar), mas é o equivalente a um método GET versus POST no HTTP: uma dica de intenção.

bloco A · servidor

O processo fica esperando no stdio

Não chamamos uvicorn. O cliente MCP é quem inicia o Python. O mcp.run(transport="stdio") entra num loop: lê JSON da entrada, executa, escreve JSON na saída.

app/mcp_server.py — if __name__
bootClique para ver
if __name__ == "__main__": from app.config import DATABASE_URL if not DATABASE_URL: print("[assessor-financeiro] DATABASE_URL ausente no .env", file=sys.stderr) mcp.run(transport="stdio")
Não rode isso “para ver se abre uma janela”

Se você executar python app/mcp_server.py no terminal, o processo trava esperando JSON-RPC. Parece hung. É o comportamento certo. Quem fala com ele é o Cursor, não você digitando.

O .env já é lido

Como importamos app.tools.financeiro, o app.config carrega o .env uma vez — a mesma regra da Etapa 2. Não coloquem load_dotenv() de novo no servidor MCP.

Este é o slide que fecha o argumento M + N. Zero mudança em mcp_server.py. Só outro host lendo um JSON no mesmo formato.

A frase do quadro

Um servidor. Dois clientes. Nenhuma linha nova no SQL. Isso é o protocolo trabalhando — não “mais uma lib Python”.

Cline não é obrigatório para passar na etapa

O checkpoint mínimo é o Cursor. O Cline é a prova extra de interoperabilidade. Se a máquina da escola só tiver Cursor, a ideia ainda está inteira — o professor demonstra o segundo cliente no projetor.
